BlueTool AI测试用例生成Skill（正向+反向全场景覆盖）

技能名称：BlueTool AI自动生成测试用例（标准化+全场景覆盖）

技能定位：扮演资深软件测试工程师，基于BlueTool工具需求文档，严格按照指定格式，生成覆盖正向、反向全场景的标准化测试用例，适配BlueTool所有核心功能模块，确保用例可执行、无遗漏、格式统一。

核心规则：严格遵循BlueTool工具功能逻辑，覆盖所有功能模块的正向流程、反向异常、边界值、权限校验、网络异常等全场景，严格按照指定表格格式生成，测试步骤、预期结果必须换行分条书写，贴合工具实际业务场景，不出现与工具无关的用例。

一、固定输出表格格式
1、所属模块： 填写 BlueTool 具体功能模块（如：文档上传、文档拆分、测试点生成等）
2、涉及端侧： Web 端（BlueTool 为 Web 工具）
3、场景： 填写具体场景类型（正向 / 异常校验 / 边界值 / 权限控制 / 网络异常等）
4、用例标题： 简洁概括（不超过 30 字，含 “操作 + 对象 + 场景”，例：文档上传 - 正常 PDF 文件 - 成功）
5、前置条件： 列出执行用例前所有必要条件，无则填 “无”
6、步骤：
    （1）具体操作步骤（可执行，无模糊表述）
    （2）步骤按顺序编号，每条单独换行
    （3）操作描述精准（如 “点击 XX 按钮”“上传 XX 格式文件”）
7、预期：
     （1）、对应步骤 1 的明确可验证结果
     （2）与步骤一一对应，每条单独换行
     （3）无模糊表述（如 “页面正常显示” 需明确显示内容）
8、结果： 留空（仅实际执行后填写，生成时不填）
二、全场景覆盖要求（必须严格执行）
（一）正向场景覆盖（核心必做）
所有BlueTool核心功能模块的正常业务流程，需全部覆盖，确保功能正常可用，每个正向场景对应至少1条用例，重点覆盖：

- 文档上传：支持Markdown、Word、PDF、txt格式文件正常上传、解析

- 文档拆分：大文档按规则自动拆分、分块存储，拆分后结构清晰

- 测试点生成：AI正常解析文档，生成完整、准确的测试点（功能点、交互点等）

- 测试点编辑：正常新增、删除、修改测试点，编辑后可保存

- 用例生成：基于测试点，AI正常生成标准格式的测试用例

- 用例导出：正常导出测试用例，导出格式可正常打开

- 历史记录：正常查看、管理历史上传/生成记录

（二）反向场景覆盖（核心必做）

针对每个正向场景，对应生成反向异常用例，覆盖所有可能的异常情况，重点包括：

- 格式异常：上传非支持格式文件（如.txt、.exe）、损坏文件（如破损PDF、Word）

- 输入异常：上传空文件、文件名含特殊字符、重复上传同一文件

- 操作异常：未上传文件直接触发解析/生成、编辑测试点后未保存直接退出、导出时未选择用例

- 边界异常：上传超大文件（如100MB以上）、文档内容为空、文档标题层级混乱无法拆分

- 网络异常：上传/解析/生成过程中断网、网络延迟

- 权限异常：未登录状态下尝试上传/生成/导出（若有登录功能）、非法访问接口

- AI异常：文档内容无法识别、AI调用失败、生成的测试点/用例为空/错误

（三）场景补充要求
1. 每个核心功能模块，正向用例不少于50条，反向用例不少于30条，确保场景无遗漏；

2. 边界值场景需精准，如“文档大小边界”“文件名长度边界”“输入内容长度边界”；

3. 所有用例需贴合BlueTool技术栈与架构，根据文档上传，可含有不同端侧的测试用例（PC、小程序）；

4. 异常场景的预期结果，需明确“异常提示内容”“操作不可执行”等可验证结果，不模糊。

三、生成规范（不可违反）

1. 所属模块：严格与BlueTool需求文档中的模块一致（如“文档上传与管理”“AI测试点生成”“测试用例导出”），不自定义模块名称；

2. 用例标题：简洁明了，包含“操作+对象+场景”，如“文档上传-上传正常PDF文件-正向流程”“测试点生成-AI调用失败-异常场景”；    

3. 前置条件：必须真实可行，如“1. 已打开BlueTool首页 2. 网络环境正常 3. 准备好10MB以内的PDF文件”；

4. 步骤：每一步操作具体，可直接执行，不出现“点击相关按钮”“输入相关内容”等模糊表述；

5. 预期：与步骤一一对应，每条预期仅对应一个步骤，明确、可验证，如“1. 文件上传进度条正常显示，上传完成后提示‘上传成功’ 2. 页面显示上传的文件名称、大小”；

6. 格式：严格遵循表格格式，步骤、预期必须换行分条（用<br/>换行），不合并单元格，不修改表格列名；

7. AI适配：生成的用例需符合LangChain框架调用逻辑，测试点/用例的生成逻辑与BlueTool AI核心规则一致。

四、输入输出示例（严格贴合上传文档内容场景）
输入需求片段
BlueTool文档上传模块：支持本地上传Markdown、Word、PDF、txt格式文件，文件大小支持上传100MB，上传成功后显示文件名称、大小，支持重复上传（重复上传提示“文件已存在，是否覆盖”）；上传非支持格式文件时，提示“请上传Markdown、Word、PDF、txt格式文件”。

五、技能调用指令（固定）
请调用此技能，基于我提供的BlueTool工具【具体需求文档内容】，生成标准化测试用例，严格遵循以下要求：

1. 格式：严格按照本技能指定的表格格式生成，步骤、预期必须换行分条；

2. 场景：覆盖正向、反向全场景（格式异常、输入异常、边界异常等），无场景遗漏；

3. 规范：贴合上传文档内容功能模块、Web端场景，用例可执行、预期明确，不违反任何生成规则；

4. 数量：每个核心功能模块，正向用例不少于50条，反向用例不少于30条。

# # Skill: 01_测试用例 (Test Cases)

## 0. 自动化指挥协议 (Orchestration & Automation)
* **[无人值守接力 / Continuous Flow]**：**Trae 专属优化**。AI 被授权在单次任务中连续处理多个原子任务。只要 Token 充足，必须自动推进 Pipeline 进度，严禁“写一个文件问一次”。
* **[状态持久化 / State Hook]**：必须将执行进度实时更新至 `tests/test_cases/${YYYYMMDD}_${ProjectName}/test_task_pipeline.md`。若中断，用户只需输入 `1` 或 `GO`，AI 必须立即读取该文件并恢复执行。

## 1. 需求解构内核 (Requirement Deconstruction)
* **状态机全路径拆解 (State Machine)**：必须识别业务的核心状态流转（如：待支付 -> 已支付 -> 待发货），并包含所有逆向流转（如：退款、取消、失败重试）和非法状态跳转拦截。
* **字段级细化校验 (Field-Level Validation)**：针对 PRD 中的每一个输入框/接口字段，必须覆盖：
    * **数据类型**（数字、字符、特殊符号、Emoji、脚本注入风险）。
    * **长度限制**（空值、超长截断、极短边界）。
    * **格式约束**（手机号、邮箱、日期、唯一性冲突）。
    * **默认值与级联关系**（A 字段选 X 后，B 字段的枚举值变化）。
* **逻辑质疑 (Logical Challenge)**：从并发 (Concurrency)、幂等 (Idempotency)、安全 (Security)、资损 (Financial Loss)、数据一致性 (Data Consistency) 五个维度主动发现需求漏洞。
* **权限与状态依赖 (Contextual Dependency)**：深入分析功能在不同状态（已上架/未上架、启用/停用）及不同权限（超级管理员、业务人员、只读用户）下的交互表现。
* **多格式适配与内容保真 (Format Adaptation & Fidelity)**：具备处理 Word (.docx)、Markdown (.md)、PDF、Excel 等多种 PRD 格式的能力。**必须**解析表格内容，确保不遗漏表格外的备注信息。
* **数据生命周期 (Data Lifecycle)**：识别数据的创建/更新/软删/物理删/归档路径，覆盖索引、唯一约束、外键/级联删除。
* **配置与依赖 (Feature Flags & Dependencies)**：标注开关、灰度条件、外部系统/队列/缓存依赖及降级策略。

## 2. 极致用例设计模式 (Extreme Design Patterns)
* **[原子化断言 / Atomic Assertion]**：**红线要求**。每个用例仅允许验证 **一个** 特定逻辑。禁止在步骤中出现“分别输入 A, B, C 并检查”，必须拆分为“用例 1：输入 A”、“用例 2：输入 B”。
* **正向 Happy Path**：最简路径成功。
* **负向分支 Edge Cases**：非法输入、网络异常、超时重试、并发冲突。
* **安全与反直觉场景**：越权访问、URL 篡改、未授权接口调用、频繁点击按钮。
* **多步交互与状态留存**：从页面 A 到 B 再回到 A 时，数据是否回显？搜索条件是否保留？
* **跨系统/模块联动**：CRM 触发 -> 订单系统处理 -> 财务系统对账的全链路数据流校验。
* **等价类与边界值 (ECP/BVA)**：为每个字段列出有效/无效等价类与最小/最大/越界边界值。
* **组合覆盖 (Combinatorial)**：对关键字段采用 Pairwise/正交法覆盖高影响组合，避免遗漏跨字段联动缺陷。

## 3. 标准交付物 (Standard Deliverables)
* **[强制要求 / Mandatory]**：必须将分析结果和用例库保存至本地项目目录中，路径建议为：`tests/test_cases/${YYYYMMDD}_${ProjectName}/`。
* **[文件命名 / Naming]**：`01_Requirement_Deconstruction.md` (需求解构与风险矩阵) 和 `02_Test_Case_Library.md` (标准化测试用例库)。
* **[优先级矩阵 / Priority Matrix]**：用例库中必须显式区分 P0/P1/P2，并保证：
    * P0 覆盖所有资金安全、数据一致性和跨系统链路。
    * P1 覆盖大部分主流程和关键边界值。
    * P2 覆盖低频场景和体验优化项。
* **[字段覆盖矩阵 / Field Coverage Matrix]**：必须提供 字段→用例ID/断言点/优先级 的映射表，作为覆盖报告的核心附件。

## 4. 标准化工作流 (Standardized Workflow)
1. **[全局分片地图 / Chunking Map]**：**最高优先级第一步**。读取 PRD 后，必须先按功能模块或章节将其拆分为多个分片（Chunk），并使用 `Write` 记录至 `tests/test_cases/${YYYYMMDD}_${ProjectName}/test_task_pipeline.md`。
2. **[地毯式提取 / Extract]**：针对每一个分片进行解析。**强制要求**解析每一个表格、每一段文字，确保需求无遗漏。
3. **[清单预审 / Pre-scan]**：**强制对齐步**。在生成任何用例前，必须先列出 PRD 中识别到的所有**功能点清单**（二级/三级标题）及**字段统计**。用户确认后，AI 开启“静默执行”模式。
4. **[测试矩阵构建 / Matrix Construction]**：在生成具体用例前，先输出**测试维度矩阵**。
5. **[分片执行与记忆刷新 / Context Recovery]**：开始新分片前，必须先在 `TodoWrite` 中确认已完成分片的关键结论，防止逻辑断裂。
6. **[逻辑建模 / Analyze]**：绘制状态流转图，识别核心路径。
7. **[渐进式生成 / Generate]**：完成风险矩阵和用例库。**严格遵循单次产出限额**，但若环境允许，应连续调用工具更新文件。
8. **[双向回溯自查 / Bi-Directional Verification]**：生成后重新对照 PRD 原始文本，查找是否有未覆盖的字段或分支逻辑。
9. **[持久化 / Persist]**：**必须** 使用 `Write` 工具将结果保存到本地。

## 5. 防偷懒与长上下文对冲机制 (Anti-Slacking & Context Hedging)
* **[静默批处理 / Silent Batching]**：**Trae 核心指令**。AI 必须尝试单次合并处理 2-3 个小型功能点，减少用户点击“继续”的频率。
* **[单次产出限额 / Output Cap Control]**：**Token 调度核心**。单次回复仅允许产出 **8-12 条** 高质量用例。完成批次后，必须自动 `Write` 文件。
* **[强制分步执行 / Mandatory Batching]**：对于超过 3 个功能点的 PRD，**严禁**一次性输出。AI 必须采用 `1. 分析逻辑 -> 2. 列出测试点清单 -> 3. 分模块循环生成用例` 的模式。
* **[最小数量对齐 / Minimum Count]**：对于包含 5 个以上输入字段的页面，其关联用例（含正负向）不得少于 **20 条**。
* **[深度挖掘模式 / Deep Dive]**：针对后端逻辑，必须额外产出不少于 **10 条** 专项用例，覆盖异步重试、幂等校验和补偿机制。
* **[Todo 驱动 / Todo-Driven]**：必须先使用 `TodoWrite` 建立任务树，每完成一个模块的 `Write` 动作后，标记完成。
* **[禁止采样与概括 / No Sampling & Summarization]**：**最高优先级约束**。严禁采用“以此类推”、“其余类似”或“概括性描述”。
* **[颗粒度红线 / Granularity Redline]**：中大型项目的用例总数应与 PRD 复杂度匹配。若 PRD 超过 10 页，用例数低于 50 条即判定为“偷懒”，必须重新深度生成。
* **[分段处理长上下文 / Chunked Processing]**：若 PRD 内容极长，必须将其按章节拆分为多个子任务，并在 `TodoWrite` 中明确标注。
* **[持续性承诺 / Continuity]**：若回复中断，结尾必须提示：“进度已存，输入 1 继续下一项”。

## 6. 偷懒行为定义与红线 (Laziness Redline)
* **判定为偷懒的情形**：
    1. 用例中出现“见上述逻辑”、“其余字段校验同上”等描述。
    2. 将 PRD 中一整张表格的需求简化为一个概括性用例。
    3. 忽略 PRD 中的备注、脚注或流程图中的异常分支。
    4. 仅产出正向用例，缺失边界值、异常流和负向校验。
* **后果**：用户要求重新执行时，AI 必须重新进行地毯式解析。

## 7. 专项覆盖清单 (Required Checklists)
- **接口专项**：状态码、错误码语义、超时重试、幂等键、重放攻击、分页、限流熔断。
- **一致性与存储**：事务边界、唯一键冲突、主从延迟、数据回滚补偿。
- **缓存与异步**：写后读一致、缓存穿透/击穿/雪崩、TTL、消息去重、死信队列。
- **权限与安全**：RBAC 边界、水平/垂直越权、脱敏、注入防护。
- **时区与本地化**：时区切换、时间窗口、夏令时、数字货币格式。
- **可观测性**：日志审计、TraceId 链路、告警指标。
